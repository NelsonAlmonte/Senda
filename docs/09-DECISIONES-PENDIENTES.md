## B. Abierto: requiere validación antes de su fase

1. **Compatibilidad de integraciones PWA:** **SvelteKit 3.1.0 ya está decidido y no debe sustituirse unilateralmente**. Se verificó que `@vite-pwa/sveltekit@1.1.0` solo declara peers para SvelteKit 1/2; por aprobación del equipo, Fase 0 usa `vite-plugin-pwa@1.3.0` directamente. El 2026-10-26 se confirmó `injectManifest` para Web Push, con un worker propio y precache estático. Revisar futuras versiones del wrapper antes de reconsiderarlo; no cambiar a SvelteKit 2 ni forzar dependencias.
2. **Lecturas:** la idempotencia por UUID, el reingreso mediante dos `INSIDE` y la regla de no retroceder el estado con datos atrasados ya están decididos. Quedan por cerrar los saltos físicamente imposibles si el hardware real demuestra que requieren filtrado adicional.
3. **Invitaciones por email:** el acceso inicial por código ya está definido. Queda decidir cómo enviar correos personalizados con Supabase + Gmail y cómo un ADMIN invalida una invitación PENDING; no crear estado EXPIRED. Esta función concede acceso a un paciente y es independiente de Web Push.
4. **Aspecto visual:** colores y tipografía definitivos continúan abiertos. Lucide ya está confirmado para la navegación; shadcn-svelte queda aplazado hasta que exista una necesidad concreta. El 2026-10-29 se eligió para `/patients` la dirección serena/editorial y se retiraron el selector y la alternativa expresiva/bento. También se aprobó una escala breve de elevación con sombras estándar de Tailwind y un header opaco sin blur. La dirección ya se extendió a las operaciones de paciente y al mapa; falta validarla en móvil y escritorio antes de aplicarla al resto de módulos.
5. **Privacidad:** retención de historial, exportación/eliminación de datos y procedimiento de consentimiento/autorización para uso real (en simulaciones, trabajar con datos ficticios).
6. **Hardware real:** modelo exacto comprado, alimentación, modem, SIM, provisioning, autenticación de dispositivo, claim y asignación física.
7. **Métricas objetivo:** fijar criterios cuantitativos para latencia de episodios, errores tolerables y rendimiento con pruebas controladas.
8. **Historial de episodios por paciente:** crear `/patients/:id/episodes` para consultar todos los episodios autorizados de un paciente, con paginación o carga progresiva. Hasta entonces, el mapa muestra únicamente los cinco más recientes y mantiene deshabilitado **Ver todos los episodios**; no debe redirigir al feed global como sustituto.

## C. Divergencia con el texto de tesis — requiere conciliación

En la versión aportada de `Proyecto Final.pdf`, el objetivo general y apartados de arquitectura/base teórica mencionan **MQTT**. El equipo posteriormente eligió **HTTPS** para comunicarse con Supabase. Ambos no deben presentarse como si fueran el mismo protocolo, ni se debe declarar haber implementado MQTT sin hacerlo.

**Acción documental pendiente:** al actualizar la tesis, ajustar objetivos y justificación tecnológica con la supervisión académica para reflejar el protocolo realmente implementado; no modificar el archivo del trabajo por cuenta propia.
